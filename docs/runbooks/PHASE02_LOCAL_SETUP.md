## 3. Run the real local app

Use the **actual local publishable key and API origin** reported by the running stack. Public values are safe to give to browsers; never use a secret/service key. Scripts do not automatically load `.env`.

```powershell
$env:MIZNORA_SUPABASE_URL = '<actual local API origin>'
$env:MIZNORA_SUPABASE_PUBLISHABLE_KEY = '<actual local sb_publishable_ key>'
$env:MIZNORA_ALLOW_SIGNUP = 'false'
npm run start:app
```

The placeholders are not working configuration. Default frontend URL is `http://127.0.0.1:4200/`. Missing/invalid configuration shows a setup error; an unavailable backend shows an error/empty state and never synthetic success. Sign in with a seeded verified identity, choose a business, and open **Manage access** as an owner. Other roles receive an explicit denied page for owner routes. Create/change/revoke invitations or member access only through the controlled RPC-backed forms. Ownership transfer requires an active verified member and explicit acknowledgement.

The **Create first business** command is idempotent and limited to one bootstrap per identity. Existing owner fixtures cannot create unlimited extra businesses. Use the non-member fixture for a fresh bootstrap test after a reset.

## 4. Signup, confirmation and recovery

Registration defaults off in both `supabase/config.toml` `[auth].enable_signup` and generated public `allowSignup`. To test registration deliberately, enable **both** the server setting and `MIZNORA_ALLOW_SIGNUP=true`, restart the local stack/app as needed, and leave `[auth.email].enable_confirmations=true`. The server minimum password length is 12. UI visibility is not the security boundary; disabled registration must also remain disabled in Supabase Auth.

Local exact redirects are already reserved in config:

```text
http://127.0.0.1:4200/auth/callback
http://127.0.0.1:4200/auth/recovery-callback
```

Confirmation/recovery mail goes to the local mail sink configured on port 54324 when the stack runs; do not configure a live sender for this phase. Finish a link in the same browser/device that requested it. The SDK stores the PKCE verifier; one explicit callback exchanges the code with URL auto-detection disabled. Codes are scrubbed and duplicate exchange calls reuse one promise. A wrong-browser/expired/consumed link shows a retry path. Refreshing the reset-password form deliberately requires a new recovery link because the verified recovery marker is memory-only. A URL `type=recovery` never authorizes a password reset. [Supabase PKCE](https://supabase.com/docs/guides/auth/sessions/pkce-flow).

Invitation links are generated by an owner and displayed once. No invitation email is sent. Tokens are email-bound, hashed in the DB and expire after seven days. The invitee signs in with the intended verified email and accepts the token. The SPA can keep a draft token in memory across sign-in; reopening the original link is required after reload loses that draft. Reissuing revokes the prior pending link for that business/email; changing an accepted member uses member access management.
